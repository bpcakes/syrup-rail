# Harden and prepare the Syrup Rail 0.2.0 release

This living ExecPlan prepares the already-implemented 0.2 billing behavior for
downstream use and publication. It deliberately adds no new billing semantics.
It makes the supported Rust facade intentional and documented, demonstrates a
safe host-owned billing-event envelope, verifies the declared Rust minimum and
dependency policy in CI, packages consumer documentation and proprietary terms,
and performs the coordinated 0.2.0 metadata cutover.

The repository security baseline is `docs/security/threat-model.md`. The event
example introduced here does not create a new security boundary: hosts still
authenticate and authorize subjects, own the outbox schema, and choose any
external transport. The example must not persist provider credentials, payment
tokens, billing contacts, raw gateway diagnostics, or raw idempotency keys.

## Surprises & Discoveries

- The normal rustdoc gate passes because missing documentation is not enabled.
  `RUSTDOCFLAGS='-W missing-docs' cargo doc --workspace --no-deps --locked`
  reported 1,959 warnings: 1,429 in `syrup-rail`, 395 in
  `syrup-rail-postgres`, 125 in `syrup-rail-nmi-client`, and 10 in
  `syrup-rail-nmi`. Much of the core count is generated by reusable value-type
  macros or belongs to low-level cross-crate contracts, so documentation should
  be added at the owning abstraction and exports must be made explicit before
  enabling a failing lint.
- `cargo +1.88.0 check --workspace --all-targets --locked` succeeds locally,
  but the ordinary and release workflows install the moving stable toolchain
  and therefore do not continuously prove the declared 1.88 MSRV.
- Current `cargo audit` reports only RUSTSEC-2023-0071 for `rsa 0.9.10`.
  `cargo tree --workspace --all-features --target all -e all -i rsa@0.9.10`
  is empty: the package is locked through SQLx's unused MySQL feature and is
  not in a workspace build graph. There is no fixed release. The repository
  needs a narrow documented exception plus a guard that fails if `rsa` ever
  becomes reachable.
- Only `syrup-rail-nmi-client` currently packages a crate README. No published
  package contains the proprietary terms referenced by the workspace license
  metadata.
- Replacing facade globs with explicit re-exports preserved the public item
  inventory exactly: `syrup-rail` remained at 290 items and
  `syrup-rail-postgres` at 165, with no added or removed paths relative to the
  pre-change tree. The later review correction intentionally adds the core
  `PaymentCardBrand` projection type before 0.2.0; that is the only subsequent
  inventory addition rather than an accidental facade change.
- Compiling the new package READMEs as crate documentation immediately caught
  an incomplete core example (`PlanKey` was omitted). Keeping README examples
  under doctest therefore provides useful consumer-level contract coverage.
- A compiler-diagnostic snapshot for the remaining legacy documentation debt
  was technically possible but disproportionate here: it required a custom
  parser and roughly 1,800 version-sensitive records while encouraging
  mechanical comments. The smaller durable policy is explicit facade exports,
  targeted `warn(missing_docs)` only on complete integration modules, and CI
  that promotes those warnings while building docs and running doctests.
- Cargo metadata defaults example targets to `test = false`; an explicit
  `[[example]]` declaration is required for the redaction assertions embedded
  in `host_integration` to run under the normal workspace test command.
- An advisory-ID ignore applies across affected package versions. Its matching
  reachability guard must therefore inspect every reachable `rsa` version, not
  only the version currently present in the lockfile.
- A temporary-index simulation of the changed-file LOC gate found that adding
  rustdoc to `subscription_billing_service.rs` pushed its stable facade from
  971 to 1,019 lines, above the 1,000-line absolute cap. Extracting the
  exhaustive disposition policy into its own 345-line owner reduced the
  facade to 690 lines; the complete simulated changed-file gate then passed.
- The first locked final test run exposed a nondeterministic schema-fixture
  failure. Random UUID decimal runs were embedded in mock provider references,
  and an unlucky value could satisfy the raw-card detector when durable state
  was decoded. A shared letters-only UUID encoding now preserves fixture
  uniqueness without resembling card data; the isolated migration scenario
  and the complete locked suite then passed.

## Decision Log

- Decision: perform a direct 0.1.1-to-0.2.0 metadata cutover.
  Rationale: the changelog and completed feature plans already identify the
  Rust API and schema changes as the intentional 0.2 breaking release; no
  mixed-version compatibility claim is valid.
- Decision: retain `BillingEvent` as a closed, provider-neutral Rust enum and
  keep serialization host-owned.
  Rationale: an exhaustive host mapper must fail to compile when a new domain
  event needs an explicit durable representation. Deriving `Serialize` on the
  domain enum would accidentally turn Rust layout choices into a wire contract.
- Decision: the example envelope owns a database-observed occurrence time,
  host event identifier, subject, stable host kind/version, semantic key, and
  minimized payload. It uses the coordinator-supplied subject retained by the
  transaction adapter and enforces idempotency in the host outbox. The type
  separates the first successful write's identifier/time from a replay value
  whose equality covers version, subject, event kind, semantic key, and
  payload. The example's concrete helper inserts on the supplied transaction,
  selects a semantic-key conflict through that same connection, reconstructs
  all split columns through checked V1 decoders, and accepts only exact replay
  equality. V1 owns its nested enum labels; a future core label change cannot
  silently alter this durable version.
  Rationale: identifier/time are first-write transport facts; accepting a
  semantic-key conflict requires every other durable fact to agree.
- Decision: record a single advisory exception only for unreachable
  RUSTSEC-2023-0071 and pair it with a dependency-graph reachability check.
  Rationale: silently ignoring an advisory would permit a future SQLx feature
  change to make the vulnerable implementation active.
- Decision: distribute a short no-license-grant proprietary notice through
  Cargo's `license-file` metadata instead of retaining an unresolvable custom
  SPDX reference with no packaged terms.
  Rationale: consumers must receive the actual governing notice; no new right
  is granted by this documentation-only change.
- Decision: enforce complete documentation immediately on the event, billing
  service, and transaction boundaries through source-level warnings promoted
  to errors by the all-feature CI rustdoc command. Do not maintain a custom
  compiler-diagnostic baseline for the remaining low-level surface; expand the
  source lint only when another owning module has meaningful complete docs.
  Rationale: new public surface is blocked today, critical contracts are fully
  described, and maintainers can pay down existing debt without normalizing
  low-value boilerplate or coupling the repository to compiler diagnostic
  prose. Avoiding a published `deny` also prevents future compiler lint
  expansion from becoming an involuntary downstream build break.
- Decision: pin every third-party GitHub Action to a full commit SHA while
  retaining the corresponding release tag in a comment.
  Rationale: CI and release behavior must not change when a mutable tag moves;
  comments preserve maintainability without weakening reproducibility.
- Decision: keep service-error variants and redacted formatting on the stable
  facade, but own exhaustive classification and retry helpers in
  `subscription_billing_service/error_disposition.rs`.
  Rationale: classification remains one closed policy table while the primary
  service facade stays below repository size limits and workflow modules do
  not duplicate operational decisions.
- Decision: retain exact provider card-brand text only in processor evidence
  needed for 0.1 replay and reconciliation, and derive the closed
  `PaymentCardBrand` value at billing-portal and host-event projections.
  Rationale: canonicalizing persisted evidence would make legacy values such as
  `Visa` and `visa` compare differently after upgrade; projecting later drops
  arbitrary provider text without changing durable identity.
- Decision: terminate standard error-source traversal at wrappers around
  arbitrary host callback errors and expose the original only through the
  consuming `into_source()` method.
  Rationale: a redacted wrapper is not a real confidentiality boundary if
  ordinary error reporters can continue into an untrusted host source.

## Context and orientation

The core public facade is `crates/syrup-rail/src/lib.rs`; its domain events are
in `crates/syrup-rail/src/event.rs`. The PostgreSQL service and transaction
ports are exposed by `crates/syrup-rail-postgres/src/lib.rs`, with the compiled
host example at `crates/syrup-rail-postgres/examples/host_integration.rs`.
Workspace publication metadata lives in `Cargo.toml`, crate manifests live
under `crates/*/Cargo.toml`, publication validation is
`scripts/check-release.sh`, and CI is under `.github/workflows/`.

The current schema is PostgreSQL-18-only schema v2. This effort must not modify
`crates/syrup-rail-postgres/schema/v1/**`, schema-v2 SQL, or committed `.sqlx`
metadata. Package file-set changes may include schema artifacts unchanged.

## Idempotence and recovery

All source and metadata changes are ordinary Git edits. Package, documentation,
MSRV, advisory, SQLx, contract, and test commands are repeatable. No migration
or external service mutation is performed. If a package validation fails,
inspect its generated file list before changing include/exclude metadata; never
rewrite an existing schema artifact. If an advisory database is unavailable,
retain the graph-reachability gate and rerun the advisory check when network
access returns rather than weakening policy.

## Interfaces and dependencies

The Rust billing-domain API remains typed and provider-neutral. The host event
example may add host-only DTOs and conversion helpers inside the example, but
no Serde dependency is added to `syrup-rail` for event serialization. CI may
install a pinned audit tool or use the already supported repository toolchain;
runtime crate dependencies must not grow for release tooling.
